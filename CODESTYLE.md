# Кодстайл

Базовые правила (длина строки, перенос аргументов `if`, английский язык логов/исключений) — в
`~/.claude/CLAUDE.md`, общие для всех проектов. Здесь — то, что специфично для Pine & Ember и не
покрывается `ruff format`/`ruff check` автоматически.

## Имена переменных в циклах и comprehension'ах

Не используем однобуквенные имена (`r`, `t`, `s`, `c`) для строк БД, задач, тегов и т.п. — даже если
короткое имя один раз сэкономит горизонтальное место, при повторном использовании `r.something`
в нескольких соседних строках оно перестаёт быть очевидным, что это за `r`. Имя должно называть
сущность: `row`, `status`, `tag`, `task`, `topic`, `concept`.

```python
# плохо
tag_list = [Tag(key=r.key, label=r.label) for r in conn.execute(select(models.Tag))]

# хорошо
tag_list = [Tag(key=row.key, label=row.label) for row in conn.execute(select(models.Tag))]
```

**Исключение:** если однобуквенное имя в тесте напрямую повторяет тестовые данные (например,
переменная `a` хранит ответ на `POST .../topics {'name': 'A'}`), оставляем как есть — так assert-ы
читаются нагляднее, чем `topic_a`/`topic_b`/`topic_c`.

## Тайп-хинты обязательны везде, включая приватные методы

Если порт (`ports.py`) объявляет сигнатуру метода с тайп-хинтами на всех параметрах, конкретная
реализация в `repository.py` обязана повторить их один в один — не оставлять `title=None` без
аннотации только потому, что метод "и так понятно, что делает". Несовпадение сигнатур порта и
адаптера — сигнал, что кто-то один из них не проверили при последней правке.

## Комментарий `ponytail:` для осознанных упрощений

Если решение осознанно срезает угол (заглушка вместо полноценной обработки, захардкоженное значение
для случая "почти никогда не происходит") — помечаем комментарием `# ponytail: <что упростили>,
<когда апгрейдить>`, а не молча оставляем магическое значение без объяснения:

```python
if row:
    return row.key
label = 'Backlog'  # ponytail: первый статус на пустой доске, явной метки не дали
```

## Пустые строки внутри функции разделяют шаги, а не украшают код

Внутри методов репозиториев устоявшийся паттерн: (1) достать текущую строку и проверить, что она
существует → пустая строка → (2) посчитать новые значения полей одно за другим → пустая строка →
(3) выполнить `UPDATE`/`INSERT` и вернуть результат. Не сжимаем это в один блок без отступов —
пустая строка перед `conn.execute(update(...))` — это визуальная граница "закончили считать, дальше
пишем в БД", а не эстетика.
