# 0012 — Финансы: учёт расходов и доходов

**Статус:** backend done (критерии приёмки ниже реализованы и покрыты тестами; фронтенд дашборда
рендерит пустое состояние и ещё не подключён к этому API, UI для CRUD операций/категорий не
существует — следующий шаг, отдельно от этой спеки)

**Примечание по реализации:** обнаружились две проблемы, не описанные в плане:
1. Python 3.14 (PEP 649, ленивая оценка аннотаций) ломает Pydantic-схемы, где имя поля совпадает с
   именем его типа (`date: date`) — имя поля перекрывает тип в пространстве имён класса. Фикс —
   `import datetime` и `date: datetime.date` вместо `from datetime import date`.
2. `urllib` на `uv`-managed Python (python-build-standalone) не видит системные корневые сертификаты
   macOS — реальный запрос к ЦБ РФ падает с `SSLCertVerificationError`. Добавлена рантайм-зависимость
   `certifi`, `exchange_rate.py` использует `ssl.create_default_context(cafile=certifi.where())`.

## Контекст

TRACKER-5 (из БД приложения): новая вкладка "Финансы" — личный учёт расходов и доходов по
категориям, статистика за произвольный период, дашборд. Первый заход на функциональность, не
связанную с доской задач или базой знаний — новый домен в терминах `app/domains/`.

## Вводные (зафиксированы в грумминге)

1. Нужна возможность заносить и траты, и доходы. У обеих операций есть категория.
2. Категории у расходов и доходов — **раздельные списки** (у расходов "Еда"/"Транспорт", у доходов
   "Зарплата"/"Подарок" и т.п., это разные сущности, не общий справочник).
3. Категории **создаёт пользователь сам** — по аналогии с блоками/темами в базе знаний (CRUD),
   не захардкоженный список.
4. Валюта ввода — **BYN или RUB**, на выбор при вводе операции (не произвольный ISO 4217 список).
5. Конвертация BYN→RUB считается **на бэкенде** (клиент не может подменить финансовый результат,
   секрет API-ключа, если он нужен, не улетает в браузер).
6. В БД хранится **и исходная сумма+валюта, и пересчитанная RUB-сумма, и курс** на момент операции —
   чтобы можно было восстановить историю и пересчитать при ошибке курса, а не только итоговое число.
7. Источник курса валют — на усмотрение реализации; предварительный кандидат — ЦБ РФ (публикует
   официальный курс BYN, бесплатно, без ключа) — уточнить при переходе к реализации.
8. Нужна статистика по **произвольному диапазону дат**, разбитая по категориям (форма представления —
   вопрос дизайна, не этой спеки). Статистика и дашборд показывают суммы **только в RUB** —
   исходная валюта операции (BYN/RUB) на статистику не влияет, это деталь конкретной записи.
9. Нужен дашборд — сводный обзор (что именно на нём — вопрос дизайна).
10. Операцию можно **редактировать и удалять** после создания. Курс BYN→RUB считается **один раз,
    в момент создания операции**, и переиспользуется при последующих правках той же операции — при
    редактировании суммы/категории заново к внешнему API за курсом не ходим, пересчитываем RUB-сумму
    по уже сохранённому курсу.
11. Если при редактировании меняют **саму валюту** операции (BYN↔RUB) — идём за курсом новой валюты,
    но **на дату самой операции** (`due`/дату траты), а не на дату редактирования. Это требует, чтобы
    источник курса поддерживал запрос курса на произвольную прошедшую дату, а не только "текущий
    курс" — учесть при выборе источника (кандидат ЦБ РФ это умеет: курс по дате в запросе).
12. У операции — только **дата**, без времени.

- Мультивалютность произвольного списка (только BYN/RUB, см. вводную 4).
- Конвертацию на клиенте — исключительно бэкенд (вводная 5).
- Общий список категорий для доходов и расходов (вводная 2).
- Дизайн интерфейса — предмет отдельного этапа после этой спеки.
- **Регулярные (повторяющиеся) операции** (зарплата раз в месяц и т.п.) — не в MVP. Явно
  зафиксировано как кандидат на доработку позже, а не забытая деталь: модель данных операции в
  реализации не должна закрывать дорогу к этому (например, не стоит намертво завязываться на
  "одна операция = одна ручная запись" там, где это легко избежать), но саму фичу не строим.

## Критерии приёмки (backend API)

1. Домен `app/domains/finance/` — закрытый пакет (по образцу `board`/`knowledge`): наружу торчит
   только `__init__.py` (`FinanceRepository`, `SqlAlchemyFinanceRepository`).
2. Схема — 2 таблицы, не 4: `categories(id, kind, name)` и `operations(id, category_id, amount,
   currency, amount_rub, rate, date)`. «Раздельные списки категорий» (вводная 2) реализованы через
   `kind IN ('expense', 'income')` и фильтрацию по нему, а не через отдельные таблицы. Направление
   операции (расход/доход) кодируется **знаком** `amount`/`amount_rub` (`+` доход, `-` расход), а не
   отдельной колонкой — наружу (API, dto) знак не протекает, там только положительная величина +
   `kind`.
3. Нельзя создать или переключить операцию на категорию несовпадающего `kind` — `InvalidOperation`
   → HTTP 400 (расход не может ссылаться на категорию дохода и наоборот, ни при создании, ни при
   смене категории операции).
4. `POST`/`PATCH` операции с `currency=BYN` вызывает конвертацию через ЦБ РФ
   (`https://www.cbr.ru/scripts/XML_daily.asp?date_req=DD/MM/YYYY`) **на бэкенде**; `currency=RUB`
   конвертацию не вызывает (`rate=1`). Курс сохраняется вместе с операцией (вводная 6).
5. Правка суммы/категории (без смены валюты) **не** обращается за новым курсом — пересчитывает
   `amount_rub` по уже сохранённому `rate` (вводная 10). Правка, меняющая валюту, обращается за
   новым курсом **на дату самой операции** (`date` после правки, если её тоже меняют в этом же
   запросе), а не на дату правки (вводная 11).
6. Недоступность ЦБ РФ (сеть, невалидный XML, нет курса на дату) → `ExternalServiceUnavailable` →
   HTTP 502, тело без деталей исключения (аналогично `unhandled_exception_handler`).
7. Удаление категории каскадно удаляет её операции (FK `ondelete=CASCADE`) — backend не блокирует
   удаление наличием операций; предупреждение пользователя — задача фронтенда, не этой спеки.
8. `GET /api/finance/dashboard?date_from=&date_to=` (оба параметра обязательны) возвращает
   `income_total_rub`, `expense_total_rub`, `balance_rub`, разбивку по категориям расходов и доходов
   отдельно, `balance_series` (дата → баланс нарастающим итогом с начала диапазона) и последние 10
   операций (`recent_operations`, оба направления вместе, по убыванию даты) — все суммы только в RUB
   (вводная 8), знак операции не протекает в ответ.
9. HTTP-контракт остальных доменов (board/knowledge) не меняется — весь текущий набор тестов (39)
   проходит без изменения ассертов.

## Осознанно не делаем (backend API)

- CHECK-констрейнт на `currency`/`kind` в БД — валидация на границе Pydantic (`Literal[...]`), как и
  весь остальной проект не использует DB-level CHECK, только FK.
- Оконные функции в SQL ради `balance_series` — агрегация одним проходом по строкам в Python,
  личных финансовых объёмов достаточно.
- Настраиваемый лимит `recent_operations` — константа 10.
- Отдельная колонка `kind` в `operations` — выводится из знака `amount`, чтобы не заводить два
  источника истины.
- Диапазон дат "по умолчанию" на бэкенде — решает фронтенд, `date_from`/`date_to` обязательны.
- UI для создания/редактирования операций и категорий, подключение дашборда к реальному API вместо
  пустого состояния — отдельный следующий шаг после этой спеки (см. `static/app.js::renderFinance`).
- Регулярные операции — как и раньше, не в этой версии (см. вводные).
