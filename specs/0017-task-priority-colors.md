# 0017 — Приоритет карточек и цветовая индикация

**Статус:** draft

## Контекст

TRACKER-12 (из БД приложения). Сейчас у карточки нет понятия приоритета — левая полоска карточки
(`.card { border-left: 3px solid var(--border) }`, `static/style.css:339`) всегда нейтрального цвета.
Хотим лёгкий механизм приоритета: полоска красится по срочности, а при переходе задачи в финальный
статус — всегда в зелёный, независимо от приоритета, и возвращается к цвету приоритета при возврате в
рабочий статус.

## Груминг (зафиксировано в диалоге)

1. Градаций приоритета — 5 (не 3 и не свободная числовая шкала): «даже среди срочных задач есть более
   и менее срочные» из TODO требует больше 3 ступеней, но не настолько много, чтобы плодить
   произвольную шкалу без заранее заданных подписей/цветов.
2. Значения приоритета — фиксированный набор ключей (по аналогии с уже существующими `status`/`queue`
   как enum-подобными сущностями, но здесь без произвольного создания «на лету» — это закрытый список,
   не задаётся пользователем): `critical`, `high`, `medium`, `low`, `lowest`.
3. Цвета берём из уже существующей в проекте палитры статусов (`static/app.js` seed-статусов:
   `draft #7FA37B`, `progress #FFB454`, `review #FF9E64`, `done #4F6E58`), чтобы не плодить новую
   цветовую схему — не хватает только «красного» конца шкалы, добавляем один новый цвет.
4. «Финальный статус» — не хардкод ключа `done` (он и сейчас захардкожен в `render()`,
   `static/app.js:214`, что ломается при переименовании/удалении/реордере статусов), а статус с
   максимальной `position` в текущем списке статусов — последняя колонка на доске. Полоска карточки в
   финальном статусе — всегда зелёная, цвет приоритета скрыт, но само значение приоритета у задачи не
   теряется и никак не меняется.

## Критерии приёмки

1. У `Task` — новое поле `priority`, одно из `critical | high | medium | low | lowest`, обязательное,
   значение по умолчанию — `low`. Поле есть в `TaskOut`, опционально в `TaskCreate`/`TaskUpdate`
   (если не передано при создании — `low`; при обновлении — не меняется, если не пришло).
2. Карточка на доске — цвет `border-left`:
   - `critical` → `#D9534F` (новый цвет)
   - `high` → `#C97D4F`
   - `medium` → `#D9A441`
   - `low` → `#8A9A5B`
   - `lowest` → `#4F6E58`
3. Если статус задачи — статус с максимальной `position` среди всех статусов на доске (последняя
   колонка), полоска карточки — зелёная (`#4F6E58`, тот же цвет, что у `lowest`, это финальный
   зелёный, не про приоритет) вне зависимости от `priority`. При перемещении задачи в любой другой
   статус полоска снова показывает цвет по `priority`.
4. Модалка создания задачи и панель деталей задачи получают поле «Приоритет» — `<select>` с 5
   вариантами (человекочитаемые подписи, не сырые ключи: «Критичный», «Высокий», «Средний», «Низкий»,
   «Самый низкий»), по умолчанию выбран «Низкий». Правка приоритета в панели деталей сохраняется
   так же, как остальные поля (`change` → `PATCH`).
5. Существующие задачи при миграции получают `priority = low` (совпадает с дефолтом на уровне
   приложения).
6. Остальной HTTP-контракт (knowledge/finance, весь набор из 71 теста) не ломается, кроме прямо
   упомянутого нового поля `priority` у board-роутов.

## Осознанно не делаем

- Свободный ввод приоритета текстом с автосозданием «на лету» (как у `queue`/`status`) — список из 5
  значений закрытый и фиксированный, груминг явно это исключил (см. п.2 груминга).
- Настраиваемую палитру приоритетов (цвет как параметр настроек) — цвета захардкожены в CSS/JS, как и
  остальные цвета статусов/очередей в проекте.
- Сортировку/фильтрацию карточек по приоритету — TODO просит только визуальную индикацию.
- Исправление хардкода `st.key === 'done'` в `render()` вне контекста финального статуса — трогаем
  только то, что напрямую касается вычисления финальной полоски (см. критерий 3), сам `.done`
  (зачёркивание заголовка) не переопределяем на «последняя колонка», чтобы не расширять scope тикета
  сверх приоритетов.

## Реализация

- Миграция `alembic/versions/0007_task_priority.py`: `ALTER TABLE tasks ADD COLUMN priority VARCHAR NOT
  NULL DEFAULT 'low'` (существующие строки получают дефолт автоматически).
- `app/domains/board/models/task.py`: `priority: Mapped[str] = mapped_column(server_default='low')`.
- `app/domains/board/dto.py`: `Task.priority: str`.
- `app/domains/board/repository.py`: `create_task`/`update_task` принимают `priority: str | None = None`
  (при создании — `priority or 'low'`; при обновлении — меняют, только если передано не `None`);
  без резолвинга (в отличие от `queue`/`status` тут нет lookup/создания — значение уже валидный ключ из
  закрытого списка, валидируется на уровне Pydantic-схемы).
- `app/schemas.py`: `Literal['critical', 'high', 'medium', 'low', 'lowest']` для `priority` в
  `TaskOut`/`TaskCreate`/`TaskUpdate` (невалидное значение — 422 от Pydantic, как и для остальных
  строго типизированных полей в проекте).
- `app/api/board.py`: `create_task`/`update_task` прокидывают `payload.priority` в репозиторий.
- `static/index.html`: `<select id="input-priority">` в модалке создания задачи (5 `<option>`), то же
  самое поле (`detail-priority`) — в панели деталей, вёрстка по образцу `detail-row`/`detail-field`.
- `static/app.js`:
  - `addTask()` — читает `input-priority`, отправляет в `POST /tasks`.
  - `renderDetail()` — новое поле в `.detail-row`, `change` → `saveDetail(task.id, {priority: ...})`.
  - `render()` — вычисляет финальный статус как `STATUSES` с максимальной `position`; цвет полоски
    карточки — `style.borderLeftColor`, вычисляется функцией `priorityColor(task, isFinalStatus)`.
- `static/style.css`: убрать статический `border-left: 3px solid var(--border)` цвет из `.card`
  (оставить только ширину/стиль), цвет приходит инлайн через `style` (по аналогии с тем, как уже
  задаётся `--cat-color`, `static/style.css:1105`, для категорий в финансах).

## Тесты

`tests/api/test_board.py` — новые сценарии: `priority` по умолчанию `medium` при создании без явного
значения; можно передать `priority` при создании; `PATCH` меняет `priority`, не передан — не меняется;
невалидное значение `priority` (не из 5 разрешённых) — 422.
